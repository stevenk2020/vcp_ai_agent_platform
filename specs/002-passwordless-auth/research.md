# Research: Passwordless Sign-in with Admin Allowlist

All Technical Context items are resolved; no `NEEDS CLARIFICATION` remains. Items marked
*operator input* need a value at deployment time but do not change the design.

## R-1: Service shape and libraries

- **Decision**: One FastAPI service `api` (Python 3.12, uvicorn). Async psycopg 3 with `psycopg_pool`, redis-py asyncio, Pydantic v2 models, `email-validator` for address checks, `google-auth` to verify Google ID tokens, `httpx` for the Google token exchange.
- **Rationale**: The constitution fixes Python/FastAPI for the Agent Platform and this service is its first piece, so later routers join the same app. Async drivers fit SSE streaming needed later.
- **Alternatives**: Django (heavier, brings its own user model that conflicts with the allowlist design); a separate auth microservice (an extra service to run for 50 users, violates principle IV); an auth SaaS (the allowlist and audit would live outside the platform).

## R-2: Database role and privileges for the API

- **Decision**: New role `api_rw` created in the bootstrap (password from `secrets/api_rw_password`). Migrations, run as `app_owner`, grant it exactly: `SELECT, INSERT, UPDATE, DELETE` on `app.users`, `app.allowlist`, `app.email_codes`, `app.sessions`; `SELECT, INSERT` only on `app.audit_events` (no UPDATE or DELETE, so the audit trail is append-only for the service). `USAGE` on schema `app`. No default privileges: every later table needs an explicit grant. No access to `serving` or `kb`.
- **Rationale**: Contract rule 3 of feature 001 requires a service with different access to get its own role and secret. Explicit grants keep new tables private by default (principle II).
- **Alternatives**: Reuse `app_owner` (owner can drop tables and edit audit rows; rejected); one grant-everything role (rejected).

## R-3: Session design

- **Decision**: On sign-in generate 32 random bytes, return them base64url in the cookie and store only `SHA-256(token)` in `app.sessions` with `expires_at = now + 7 days`. Every protected request looks up the hash, requires `revoked_at IS NULL`, `expires_at > now`, and the user's `status = 'active'`, and loads the user's current role from the database. Removing an allowlist entry, rejecting or suspending a user updates `revoked_at` in the same transaction. Sign-out sets `revoked_at`. No sliding expiry: 7 days from sign-in, then sign in again.
- **Rationale**: A database lookup per request gives immediate revocation (FR-010) with no cache to invalidate; at 50 users the cost is negligible. A 256-bit random token needs no slow hash. Reading the role per request means role changes apply immediately.
- **Alternatives**: Signed JWT sessions (cannot be revoked without a server-side list, which is the same lookup); sliding sessions (longer exposure, not required).

## R-4: Sign-in code design

- **Decision**: Generate the 6 digits with `secrets.randbelow(10**6)`. Store `HMAC-SHA256(pepper, email || ":" || code_id || ":" || code)` in `app.email_codes` (never the digits), plus `expires_at = now + 10 min`, `attempts`, `consumed_at`, `cancelled_at`. Verification: the newest unconsumed, uncancelled, unexpired code for the email, constant-time compare, `attempts` incremented on every try inside the same transaction with `SELECT ... FOR UPDATE`; at 5 wrong attempts the code is cancelled. Requesting a new code cancels earlier ones (FR-005). The pepper is `secrets/auth_pepper`, a random 32-byte secret generated by `make secrets`.
- **Rationale**: Only 10^6 possible codes, so a plain SHA-256 stored in the database could be reversed instantly if the table leaked; a keyed HMAC makes the stored value useless without the pepper. Row locking makes simultaneous use of one code succeed once.
- **Alternatives**: Plain hash (reversible); bcrypt/argon2 per code (slower than needed, still brute-forceable offline for 10^6 values without a pepper); signed stateless codes (cannot enforce single use and attempt limits).

## R-5: No leaking of who is allowed

- **Decision**: The request-code step never reads the allowlist: for every valid-looking email it issues and mails a code and returns the same `202` message. The allowlist is consulted only after the person proves ownership of the email (code verify or Google). Wrong, expired and consumed codes all return the same `401` error. Work done per request does not depend on the allowlist, so timing does not either; a test measures both paths.
- **Rationale**: This removes the oracle at its source instead of adding artificial delays. People outside the list can still prove their email and land in the approval queue (spec User Story 3).
- **Alternatives**: Only mail allowlisted addresses (leaks through timing and through the pending-queue requirement); constant-time padding (fragile).

## R-6: Rate limiting

- **Decision**: Redis fixed-window counters with `INCR` and `EXPIRE`. Keys: `rl:code:email:{sha256(email)}` (default 5 per hour), `rl:code:ip:{ip}` (default 20 per hour), `rl:verify:ip:{ip}` (default 30 per 10 minutes). Limits are settings. Over the limit returns `429` with one generic message and a `Retry-After` header; no email is sent. Per-code attempts (5) live in the database (R-4).
- **Rationale**: Redis is already in the stack for this purpose (spec section 2). Hashing the email keeps addresses out of Redis. Because every address gets a code, an attacker can make the service email arbitrary people; the caps bound that (accepted residual risk, noted in the spec Assumptions).
- **Alternatives**: In-process counters (lost on restart, wrong with more than one worker); database counters (more write load for a simple counter).

## R-7: Email delivery

- **Decision**: A `Mailer` interface with two backends chosen by `MAIL_BACKEND`: `smtp` (standard library `smtplib` with STARTTLS, run in a thread so the event loop is not blocked; host, port, user, password, sender from `secrets/api_external`) and `capture` (writes each message as a JSON file in a directory inside the container; used in development and tests). The service refuses to start with `capture` when `APP_ENV=production`. The email body contains the code and the 10-minute lifetime; the code is never logged. If sending fails the code created for that request is cancelled, a generic "try again later" `503` is returned and the failure is audited.
- **Rationale**: SMTP matches spec section 2 ("SMTP of a transactional email service") without tying the code to a vendor SDK. A capture backend lets tests read codes without email and without logging them.
- **Alternatives**: Vendor HTTP API clients (lock-in); logging codes in development (violates FR-019 and risks being left on).
- *Operator input*: SMTP provider and credentials, sender address and domain DNS records (SPF/DKIM) when going live.

## R-8: Google sign-in

- **Decision**: OpenID Connect authorization-code flow with PKCE and `state` (kept in a short-lived HttpOnly cookie). The callback exchanges the code, then verifies the ID token with `google-auth` (signature via Google's keys, issuer, audience equals our client id, expiry) and requires `email_verified = true`. Only the verified email is used; Google tokens are discarded after verification and never stored or logged. A small `IdentityProvider` interface lets tests inject a fake. Client id and secret come from `secrets/api_external`; if absent the Google endpoints return `503 not_configured`.
- **Rationale**: Standard, minimal and testable. Identity is the verified email at each sign-in, so an email change at Google needs no migration.
- **Alternatives**: Implicit flow (deprecated); trusting the unverified `email` claim (rejected by FR-006).
- *Operator input*: a Google OAuth client (consent screen, redirect URI `https://vcp.onepercentdata.site/v1/auth/google/callback`). Not available yet, so only the fake is exercised until then.

## R-9: Cookie, CSRF and transport

- **Decision**: Cookie `__Host-session` with `Secure; HttpOnly; SameSite=Lax; Path=/` (no `Domain`). Every unsafe method (POST, PUT, PATCH, DELETE) that relies on the cookie must send JSON and an `Origin` header equal to the configured public origin, otherwise `403`. Production runs only behind HTTPS (Caddy). In local tests the in-process client uses an `https://` base URL so the Secure flag is honoured.
- **Rationale**: `__Host-` prevents subdomain cookie injection; SameSite plus Origin checks cover CSRF without extra tokens for a JSON API.
- **Alternatives**: Double-submit CSRF tokens (more moving parts than needed here); non-`Secure` cookies (never).

## R-10: First admin

- **Decision**: A command `python -m app.cli create-first-admin --email <address>` run through `docker compose exec api` (or `run`). In one transaction under a Postgres advisory lock it refuses if any user with role `admin` exists (any status except `rejected`), otherwise creates that user as `admin`/`active` and audits `first_admin_created`. There is no environment variable, file or default account that grants admin rights, so nothing remains after use; running it again prints why it refused.
- **Rationale**: Satisfies FR-015 with a server-side action only an operator with shell access can perform. The advisory lock makes two simultaneous runs create one admin.
- **Alternatives**: Seed from an environment variable at startup (a permanent backdoor if left in place); a magic first-visitor-wins page (race and takeover risk).

## R-11: Last-admin protection and role changes

- **Decision**: Removing, suspending, rejecting or demoting an admin takes the same advisory lock, counts remaining `active` admins and refuses with `409 last_admin` if the change would leave none. Removing an allowlist entry that covers an admin's email also counts as removing that admin's access.
- **Rationale**: Prevents the system from ending up with nobody able to approve people (FR-016).
- **Alternatives**: Allow it and rely on the CLI (the CLI refuses once any admin row exists, so recovery would need database access).

## R-12: Allowlist matching

- **Decision**: Emails and domains are stored lowercase (a `CHECK` enforces it) and compared exactly. An email entry beats a domain entry when both match. A domain entry matches only that domain, not its subdomains. Adding an entry that matches a pending user does not create a session; it sets nothing until their next sign-in, when the gate finds the entry and activates them (FR-021).
- **Rationale**: Simple, predictable matching with the behaviour the spec's edge cases require.
- **Alternatives**: Subdomain wildcards (more risk of unintended access).

## R-13: Audit

- **Decision**: `app.audit_events` is insert-only for the API role (R-2). Each event stores time, actor user id and email, action name, target, outcome and IP; `detail` is a small JSON object that never contains codes or tokens (a helper rejects known secret-looking keys). Application logs use structured JSON through a filter that drops fields named `code`, `token`, `password`, `secret`, `authorization` and `cookie`.
- **Rationale**: FR-018 and FR-019; append-only access makes tampering by a compromised API role harder.
- **Alternatives**: Logging to files only (no query for admins); a trigger-based immutability on top of grants (can be added later).

## R-14: Client IP

- **Decision**: Caddy replaces `X-Forwarded-For` with the real client address; uvicorn runs with proxy headers trusted from the internal network only (the `api` container publishes no ports). The IP is recorded in audit events and used for rate limits.
- **Rationale**: Without a trusted proxy header every request would appear to come from Caddy.
- **Alternatives**: Trust the header from anyone (spoofable); ignore IPs (disables the per-IP cap).

## R-15: Secrets handling for external credentials

- **Decision**: `make secrets` also creates `api_rw_password` and `auth_pepper` (random) and an `api_external` template file (dotenv format, keys present with empty values: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`). The file always exists, so Compose never fails on a missing secret, and the service treats an empty value as "not configured". `scan-secrets` treats `api_external` like `rclone_config`: only values of keys containing password, secret, token or key count. The operator fills it when SMTP and Google are ready.
- **Rationale**: Avoids the optional-secret problem found in feature 001 without a second compose file, and keeps real credentials out of git.
- **Alternatives**: A separate compose override like the backup service (extra moving part for a file that can simply be empty).

## R-16: Testing approach

- **Decision**: Integration tests run in an `api-test` container (profile `test`, `target: test` of the Dockerfile) on the compose network: real Postgres and Redis, the app mounted in-process through httpx `ASGITransport` with an `https://` base URL, a `FakeClock` that tests advance, a `CaptureMailer` that tests read codes from, and a `FakeIdentityProvider`. The container receives `app_owner_password` (to clean tables between tests) in addition to the API's own secrets; the profile is never started in production. `make test-api` wraps it. Tests also scan the database and captured logs for readable codes and tokens (SC-006).
- **Rationale**: Real database behaviour matters (row locks, grants, hashes); injected time and mail make expiry and attempt rules testable in seconds.
- **Alternatives**: Publishing Redis to the host for tests (breaks the "Redis publishes nothing" check from feature 001); mocking the database (hides permission and locking bugs).

## R-17: Reverse proxy routing

- **Decision**: Caddy proxies `/v1/*` to `api:8000` and keeps `/healthz` as the platform health route; the API has its own `GET /v1/health` used by the container healthcheck (database and Redis reachable).
- **Rationale**: One public entry point with HTTPS already handled by Caddy.
- **Alternatives**: Publish the API directly (extra certificate and port handling).
